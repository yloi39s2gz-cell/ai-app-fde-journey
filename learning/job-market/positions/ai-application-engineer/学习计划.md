## 0. 结论先说

对"AI 应用工程师"这个岗位，你的差距**不在 AI 部分，在工程部分**。
所以本文件里 **8 条任务有 6 条跟 AI 无关**——它们是把已有的 AI 能力"包起来"的动作。

| 类型 | 任务数 | 占比 |

| AI 能力深化 | 2 | 25% |

## 1. 必修增量（按时间顺序，直接插进窗口一）

| # | 任务 | 挂在哪 | 产出（验收） | 对应 JD 要求 |
| --- | --- | --- | --- | --- |
| IN-1 | **FastAPI 服务化**：把 [fde/stage0](../../fde/stage0/) 的工单系统包一层 HTTP（`GET /tickets`、`POST /tickets`） | 窗口一 **D5**（已在原计划） | `uvicorn` 起得来，浏览器打开 `/docs` 看到接口 | 要求 7（9/11 家） |
| IN-2 | **SSE 流式**：加 `/ask`，把 stage1 的流式客户端搬到服务端 | 窗口一 **D6**（已在原计划） | `curl` 逐字返回，不是等 3 秒一次性出来 | 要求 7/8 |
| IN-3 | **原生 Function Calling**：把 [stage4/tools.py](../../ai-app/stage4/tools.py) 的手写 JSON schema 换成模型的 `tools` 参数 | 窗口一 **D9**（新插） | trace 里看到 `tool_calls` 由模型自己产生，不是你解析出来的 | 要求 4（11/11 家） |
| IN-4 | **LangGraph 双 Agent 编排**：检索 Agent → 审核 Agent，中间传递状态 | 窗口一 **D12**（旁支，可选加深） | 一张编排图；一次跨节点状态传递的 trace | 要求 5（4/11 家，在涨） |
| IN-5 | **真向量库**：装 Chroma（或 FAISS），把 [stage5/index.py](../../ai-app/stage5/index.py) 的后端换掉 | 窗口一 **D17**（旁支） | 同一张检索对比表，换成 Chroma 后端，数字不退化 | 要求 12（5/11 家） |
| IN-6 | **Docker 化 + 公网部署**：作品 Dockerfile + docker compose + 一台云主机 | 窗口一 **D26**（已在原计划） | `docker compose up` 一条命令起服务；**一个公网 URL** | 要求 9/18（8+3 家） |
| IN-7 | **应用层评测体系**（本岗位最被低估的一条） | 窗口一 **D20**（与新排任务合并） | 一份含 4 类指标的评测报告：检索质量（R@1/MRR）、生成质量（引用支持率）、安全（注入通过率）、成本延迟（token/单次成本/P95 延迟） | 要求 14（**7/11 家**） |
| IN-8 | **CI/CD**：GitHub Actions → pytest + ruff | 窗口二（第 2 个月） | README 上一个绿色 ✓ badge | 要求 11（6/11 家） |

## 3. 明确不做（防止时间被稀释）

| 不做 | 理由 |
| --- | --- |
| Java / Spring Boot | 只有 2/11 家提，且是另一条技术栈 |
| Kubernetes | 6/11 家要的是 Docker+CI/CD，K8s 是"或有"；先用 Docker 混过 |
| 多模态（文生图/3D） | 2/11 家，且需要 CV 基础 |
| 从零训练模型 | 这是算法岗，不是应用岗 |
