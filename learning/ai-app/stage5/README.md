# stage5 — 把"检索"从玄学变成一张表

> 一句话：stage3 用的是哈希向量，我给它换上真实的检索组件组合，并用两套题把
> "到底哪种检索更好"测成了数字。
> **结果是反直觉的，而且反直觉的地方才值钱。**

## 1. 为什么要有 stage5

stage3 的手写 RAG 里，`embedder.py` 的默认实现是 `HashingEmbedder(dim=256, ngrams=(2,3))`。
它把字符 n-gram 哈希进 256 维向量——**它不是语义模型，只是另一种字面匹配**。
20 题 eval 里失败的 h15，根因就是这个。

于是我想验证一个假设：

> 把"假稠密"换成"真检索组合"（BM25 + 稠密 + RRF 融合 + 重排），召回率应该明显提升。

**假设被数据部分推翻了**（详见第 5 节）。而推翻它的过程，恰恰是这一阶段最值钱的东西。

## 2. 四种检索策略

| 模式 | 实现 | 靠什么信号 |
| --- | --- | --- |
| `dense` | `HashingEmbedder` 256 维 + 余弦 | 字符 n-gram 哈希（伪语义） |
| `sparse` | 自写 `BM25(k1=1.5, b=0.75)` + 中文二字切分 | 词是否出现，带 IDF 与长度归一化 |
| `hybrid` | BM25 与 dense 各取 12 条，**RRF 融合** | 两路排名投票 |
| `rerank` | hybrid 召回 12 条 → 重排 → 取 4 条 | 候选集内重新估计 IDF |

关键设计：**四种模式共用同一份 chunk、同一套题、同一个判分函数**。
只换检索策略这一个变量，其他全不动——否则数字没有可比性。

- chunk：`chunk_size=300, overlap=60`（stage3 是 180/40，此处刻意不同，用来做消融）
- 融合：`fused(d) = Σ_r w_r / (k + rank_r(d))`，`k_rrf=60`
- 指标：文档级 Recall@1/3/4、chunk 级 Recall@4、文档级 MRR

## 3. 两套题：为什么一套不够

| 套题 | 题数 | 特点 | 用途 |
| --- | --- | --- | --- |
| `common` | 15 | 用户按制度原文的问法 | 看基线 |
| `semantic` | 15 | **刻意与原文几乎不共享 token**的同义改写 | 逼出字面检索的天花板 |

`semantic` 套题的构造方式：把「入职满 1 年不满 3 年，每年 10 天年假」
改写成「我干了两年，一年能休多少天？」——两句话几乎没有共同词。

为什么必须这么设计：5 篇文档的小语料上，BM25 会直接满分，
**看一套题只会得出"我的检索没问题"这个错误结论**。
只有 lexicon mismatch 场景才能区分"字面匹配"和"语义匹配"。

## 4. 实测结果

### 4.1 常用套题（common，15 题）

| 检索策略 | doc R@1 | doc R@3 | doc R@4 | chunk R@4 | doc MRR |
| --- | --- | --- | --- | --- | --- |
| dense | 93% | 100% | 100% | 100% | 0.967 |
| sparse | 100% | 100% | 100% | 100% | 1.000 |
| hybrid | 100% | 100% | 100% | 100% | 1.000 |
| rerank | 100% | 100% | 100% | 100% | 1.000 |

**小语料 + 忠实问法 = 所有方法都接近满分。这张表几乎没有信息量**，这就是要加第二套题的原因。

### 4.2 同义改写套题（semantic，15 题）——真正拉开差距的一组

| 检索策略 | doc R@1 | doc R@3 | doc R@4 | chunk R@4 | doc MRR |
| --- | --- | --- | --- | --- | --- |
| dense（哈希向量） | **47%** | 80% | 80% | 80% | 0.600 |
| sparse（BM25） | **87%** | 100% | 100% | 100% | 0.933 |
| hybrid（RRF 1:1） | 67% | 93% | 93% | 93% | 0.789 |
| rerank（候选集 BM25 重排） | 87% | 100% | 100% | 100% | 0.933 |

### 4.3 RRF 权重消融（semantic 套题）

| w_sparse : w_dense | R@1 | R@3 | MRR |
| --- | --- | --- | --- |
| 1 : 1（教科书默认） | 67% | 93% | 0.789 |
| 2 : 1 | 80% | 93% | 0.867 |
| 3 : 1 | 80% | 93% | 0.867 |
| 1 : 0.5 | 80% | 93% | 0.867 |
| 1 : 0.25 | 80% | 93% | 0.856 |
| 4 : 1 | 80% | 93% | 0.856 |

### 4.4 chunk 大小消融（semantic 套题，`python ablation.py --suite semantic`）

| chunk_size | chunks | dense R@1 | sparse R@1 | hybrid R@1 | rerank R@1 |
| --- | --- | --- | --- | --- | --- |
| 150 | 21 | 47% | 87% | 60% | 67%（旧重排器） |
| 300 | 18 | 47% | 87% | 67% | — |
| 500 | 18 | 47% | 87% | 67% | — |

chunk 150 → 300 只带来 hybrid R@1 的 60%→67%；300 与 500 完全一致（切出来都是 18 块）。
**结论：5 篇文档的语料上，chunk 大小不是主要矛盾。** 真实语料上这个参数才会重要
（长文档、跨段落的答案），所以这条结论要标注适用边界，不能外推。

## 5. 三个反直觉的发现（这一阶段的真正产出）

### 发现一：小语料 + 中文上，BM25 打败了"稠密向量"

同义改写套题上，sparse 87% vs dense 47%，**差 40 个百分点**。

原因不是"BM25 比向量好"，而是 **`HashingEmbedder` 压根不是语义模型**。
它把字符 n-gram 哈希进 256 维——数据结构和向量库一样，信号却还是字面重合，
而且丢掉了 BM25 的两个关键机制：**IDF 和长度归一化**。
所以它既没有语义泛化能力，又比 BM25 更粗糙。

> **这是整个仓库最容易在面试里讲错、也最容易加分的一个点**：
> "我用了向量检索"不等于"我用了语义检索"。
> 判断一个 embedder 是不是语义模型，不能看它输出不输出向量，
> 要看它没见过的同义表达能不能召回。

### 发现二：RRF 默认 1:1 融合，会把强的那一路拉下水

R@1 从 BM25 单路的 87% 掉到 hybrid 的 67%。
加一路更弱的检索器，结果**比不加还差**。

机制：RRF 里每条命中的票数是 `w / (k + rank)`，只看排名不看分数。
所以弱路的 Top-1 和强路的 Top-1 拿**一样多的票**。
弱路一条噪声就能压掉强路一条正确证据。真实失败案例（v07「在家连公司系统要先装什么？」）：

- BM25：`IT与办公.md#1`（VPN 那段）排名第 1，分数 10.33，第 2 名只有 8.51 —— 分得很开
- dense：正确文档根本不在前 5，第 1 名是「电子发票须在 5 个工作日内上传」
- 融合后：dense 的错误 Top-1 与 BM25 的正确 Top-1 拿到同样的票，正确证据被挤下去

把权重调成 2:1 后 R@1 回到 80%。**修法不是"别用混合检索"，而是"先给每一路评测，
再按质量加权"** —— 这也解释了为什么"我用了混合检索"是一句没有信息量的话。

### 发现三：一个不换信号维度的"重排器"，会把排序打散

我最初写了 `HybridReranker`：`score = 0.3 × RRF基准 + 0.7 × 字面覆盖率`。
覆盖率 = query 里的字/词有多少比例在文档里出现过。

- 它在语义套题上把 rerank 压到 67%/93%，**比不重排（hybrid）还差**
- 而且把 `base_weight` 从 0 扫到 1.0，MRR **一动不动**：
  `rerank base=0 … base=1` 全部是 0.800 —— 说明基准项完全没起作用

原因：它用的是**和 BM25 同一个信号（字面重合）**，只是没有 IDF 和长度归一化。
同一个信号数第二遍不会产生新信息，只会把强路的排序打散；而且"在/的/是"这类高频字
也等权计入覆盖率，长文档天然占便宜。

替换成 `BM25Reranker`（**在 12 条候选组成的小集合上重新估计 IDF**，统计口径变了，
所以有信息增益）后，rerank 回到 87%/100%/0.933，和不重排的 hybrid 3:1 打平，
在 150-chunk 配置下还比它高（67% → 87%）。

**两条可迁移的原则**：
1. 重排器必须换一个信号维度（真 cross-encoder 是语义维度），
   否则它只是把召回阶段的排序搅乱一遍。
2. "扫参数表里所有值结果完全一样"是一个**危险信号**，通常意味着那一项根本没生效，
   而不是"这个参数不敏感"。

## 6. 诚实的结论

1. **这套语料上，最省事的方案是 BM25 单路。** 不是我想要的结论，但它是数据说的。
2. **重排没有带来额外召回。** 因为 BM25 单路的 R@3 已经是 100%，
   召回阶段已经把正确答案捞进来了，重排只能在 Top-1/Top-3 之间调顺序。
   > 重排的上限由召回决定：召回没捞到的文档，重排不可能变出来。
3. **要验证"真语义检索到底能不能提升"，必须先换掉 embedder。**
   本环境没有 embedding key（`.env` 只有 `LLM_API_KEY / LLM_BASE_URL / LLM_MODEL`），
   `sentence-transformers` 也没装。这是**当前唯一真正的阻塞点**。
   下一步二选一：接一个 embedding API，或本地跑 `BAAI/bge-small-zh-v1.5`，
   然后**原封不动重跑这四个数字**对比。
4. **指标本身有水分**：`chunk R@4` 把目标文档的所有 chunk 都算正样本，
   所以它天然高于文档级指标。汇报数字时必须说清楚口径。

## 7. 踩过并修掉的三个 bug（都能拿去讲）

1. **协议参数顺序写错 -> 静默失效**：`reranked_search` 里写成 `reranker(hit.text, hit.text, ...)`，
   变成"文档和自己算覆盖率"，coverage 恒为 1.0，重排完全失效且不报错。
   修法：把协议 `reranker(query, document, base_score)` 写死在注释里（`index.py` 重排段）。
   **教训：靠调用方自律的参数顺序，一定要有单测兜底。**
2. **权重公式写反**：base 与 coverage 的权重颠倒，覆盖率形同虚设。
3. **导入路径**：`run_eval.py` 直接跑报 `ModuleNotFoundError: No module named 'embedder'`
   （`metrics -> index -> embedder` 依赖 stage3 在 `sys.path` 上）。
   修法：在任何本地 import 之前把 stage3 插进 `sys.path`。

## 8. 文件职责

| 文件 | 职责 |
| --- | --- |
| `tokenizer.py` | 中文分词：ascii 整词 + 中文单字 + 相邻二字组合（`A3` 保持单 token） |
| `bm25.py` | `BM25(k1=1.5, b=0.75)`，IDF = `log(1 + (N-n+0.5)/(n+0.5))` |
| `index.py` | `HybridIndex`：dense / sparse / hybrid(RRF) / reranked 四种检索 |
| `rerank.py` | `Reranker` 协议 + `HybridReranker`（覆盖率版，作为反例保留）+ `CrossEncoderReranker` |
| `bm25_rerank.py` | `BM25Reranker`：候选集内重算 IDF 的轻量重排器（当前默认） |
| `corpus.py` | 复用 stage3 语料与 chunker |
| `eval_cases.py` | 两套题 + 干扰项 + 判分函数 |
| `metrics.py` | Recall@k / MRR，纯函数，方便单测 |
| `pipeline.py` | 检索 + 生成（共用 stage3 的 prompt 约束） |
| `run_eval.py` | 主评测入口，出表 |
| `ablation.py` | chunk 大小 × 策略 |
| `weight_sweep.py` | RRF 权重 + 重排基准权重 |
| `test_stage5.py` | 16 个离线单测 |
| `reports/` | 已生成的评测报告（`.md`） |

## 9. 怎么跑

```powershell
# 离线，不花钱，秒出
python run_eval.py --suite common
python run_eval.py --suite semantic
python run_eval.py --suite all --out reports\all.md
python ablation.py --suite semantic --sizes 150,300,500
python weight_sweep.py --suite semantic
python -m pytest -q          # 16 passed

# 会调 LLM（需要 stage0 的 .env），含 3 道干扰项
python run_eval.py --suite semantic --modes rerank --with-llm
```

> 注：Windows PowerShell 5.1 不支持 `||`；中文输出先设
> `$env:PYTHONIOENCODING='utf-8'`。
