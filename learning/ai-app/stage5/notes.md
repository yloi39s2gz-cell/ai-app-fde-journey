# stage5 学习笔记 — 检索不是玄学，是一张表

> 记录原则：先写**现象**（跑出来什么、数字多少），再写**结论**，最后写**还没搞懂的**。
> 断言不写数字的笔记，三个月后自己都不信。

## 一、概念：稀疏 vs 稠密

| | 稀疏（BM25） | 稠密（embedding） |
| --- | --- | --- |
| 匹配依据 | 词是否出现 | 向量空间距离 |
| 擅长 | 专有名词、编号、密码、精确字面量（`A3`、`Welcome@2026`） | 同义改写、跨措辞语义 |
| 崩在 | 换一种说法（"带薪休假" vs "年假"） | 精确字面量；排序粒度粗 |
| 可解释性 | 高（能说清是哪个词贡献的） | 低 |

**我今天学到的关键区分**：判断"语义检索"不能看它输出不输出向量，
要看**没见过的同义表达能不能召回**。`HashingEmbedder` 输出 256 维向量，
但它是把字符 n-gram 哈希进去——数据结构是向量，信号还是字面，属于"伪稠密"。

## 二、概念：RRF（Reciprocal Rank Fusion）

```
fused(d) = Σ_r  w_r / (k + rank_r(d))        k 一般取 60
```

为什么不能直接把 BM25 分数和余弦相似度相加：**量纲不同**。
BM25 本例实测能到 10.33，余弦在 [-1, 1] 之间。直接相加的话 BM25 完全主导，
稠密那一路等于没加。RRF 只吃排名不吃分数，天然免疫量纲问题。

**但只吃排名也带来代价**：它默认两路质量相当。
本仓库的实测（semantic 套题）：

| w_sparse : w_dense | R@1 | MRR |
| --- | --- | --- |
| 1 : 1 | 67% | 0.789 |
| 2 : 1 | 80% | 0.867 |

单路 BM25 是 87% / 0.933。也就是说 **1:1 融合比不加还差**。
一条弱路的 Top-1 和强路的 Top-1 拿一样多的票，一条噪声就能压掉一条正确证据。

> 记住这句话：**"我用了混合检索"不是结论，是待验证的假设。**

## 三、概念：两阶段检索（recall-then-rerank）

- 召回要**宽**（recall_k=12，宁滥勿缺）
- 重排要**准**
- 只召回 4 条然后重排 4 条 —— **重排没有可动空间，提升必然接近 0**

**重排的上限由召回决定**：召回没捞到的文档，重排不可能变出来。
本仓库实测就撞到了这个上限：BM25 单路 R@3 已经 100%，所以重排只在 Top-1 上调顺序，
拉不动 R@3。要看到重排的价值，必须先有一个"召回不够好"的场景。

### 重排器必须换一个信号维度

我写的第一个重排器是个反例：

```
score = 0.3 × RRF基准 + 0.7 × coverage(query, 文档)
coverage = query 里有多少比例的字/词在文档里出现过
```

它是"把 BM25 用的同一个信号再数一遍"，只是没有 IDF、没有长度归一化。
实测把 R@1 从 hybrid 的 67% 压到 67%/93%（更差），
而且**把 base_weight 从 0 扫到 1.0，MRR 一动不动（全是 0.800）**。

换成"候选集内重新估计 IDF"的 `BM25Reranker` 后回到 87%/100%/0.933。
统计口径变了 → 有信息增益；同一个信号重复计数 → 只会打散排序。

> **危险信号**：扫参数时结果完全一样。那不是"这个参数不敏感"，
> 而通常意味着**那一项根本没生效**。

## 四、我今天实测到的现象（phenomena）

1. 同义改写 15 题：哈希向量 dense R@1 **47%**，BM25 **87%**。差 40 个点。
2. v07「在家连公司系统要先装什么？」：
   - BM25：正确文档（VPN 那段）第 1 名，10.33 分，第 2 名 8.51，分得很开
   - dense：正确文档不在前 5，第 1 名是「电子发票须在 5 个工作日内上传」
   - RRF 1:1 融合后：正确文档被挤到第 5 名 —— **两个错误信号合起来压掉了一个正确信号**
3. chunk 150/300/500 消融：150 → 300 只让 hybrid R@1 从 60% 到 67%；
   300 与 500 **完全一致**（切出来都是 18 块）。5 篇文档上 chunk 不是主要矛盾。
4. `chunk R@4` 指标天生比 doc 级高：目标文档的所有 chunk 都算正样本，
   只要 1 块进 Top-4 就算命中。**汇报数字必须说口径**。

## 五、工程习惯（本阶段新增）

- **一次只动一个变量**：四种检索模式共用同一份 chunk、同一套题、同一个判分函数。
- **指标要能用手算校验**：`metrics.py` 是纯函数，单测里用手算的期望值对的。
- **参数顺序写进注释**：`reranker(query, document, base_score)` 这个协议我写错过一次，
  变成"文档和自己比覆盖率"，coverage 恒等于 1，重排静默失效且不报错。
- **反例保留在代码里**：`HybridReranker` 没删，留在 `rerank.py` 当反面教材，
  注释里写明它为什么无效。删掉它，我就少了一个能讲的故事。

## 六、我还没搞懂的（下一步的问题清单）

1. **真语义模型的 dense 到底能到多少？** 阻塞：没有 embedding key，
   `sentence-transformers` 也没装。要跑 `bge-small-zh-v1.5` 才知道。
   预期：dense 的 47% 会明显上升。**如果不上升，说明是语料太小，不是模型不行** ——
   这个区分很重要，我已经准备好两种解释的判别方法（扩大语料再测）。
2. **RRF 的 k=60 是怎么定的？** 我只知道它压低了排名差异的影响，没有实测过 k 的敏感度。
3. **什么样的 query 应该走 sparse、什么应该走 dense？**
   现在是一刀切。真实系统里能不能先分类再路由？需要什么信号？
4. **cross-encoder 重排是否真的比 BM25 二次打分好？** 需要真模型才能对比。
5. **引用编号是否真的支持答案**，现在没自动判分，只查了关键词和拒答。

## 七、一句话总结这个阶段

我以为我在"升级检索"，结果我在**证伪自己**：
向量不等于语义，融合不等于更好，重排不等于提升。
三个都反了，但每反一个，我都拿到了一张有数字的表 ——
面试能讲的从来不是"我用了 X"，而是"我测了 X，它在这里没用，因为 Y"。
